# I18n

Translations with MessageFormat 2 messages, and numbers, dates and plurals formatted for the user's locale.

I18n is two traits in `rayx_app::services::i18n`, so that any implementation of the first formats alike:

- `I18nService`, a contract: the app's languages and messages, published as `I18nState`, with async commands that
  change them. Its data cross to TS, so a TS implementation can load messages from anywhere.
- `MessageFormatter`, Rust only and synchronous (for render and `tr!`), over whichever `dyn I18nService` is
  registered. RayX's compiles the service's messages per language with [dXn.I18n](https://github.com/dXnSix/dXn.I18n)
  and formats with [dXn.Intl](https://github.com/dXnSix/dXn.Intl) (ICU4X), the same on every platform. It follows
  every state the service publishes: it compiles the messages again when they change and takes a new locale or time
  zone on the next call, whatever the state's `version` says (a TS implementation need not count).

## Register

| | |
| --- | --- |
| Trait | `rayx_app::services::i18n::I18nService` and `MessageFormatter` (`rayx::app::services::i18n`; both in `rayx::prelude`) |
| Crate | `rayx_services_i18n` (`rayx::services::i18n`) |
| Feature | `i18n` |
| Rust | `add_i18n(configure)`, `add_message_formatter()` (`I18nAppBuilderExt`); `tr!` (in the prelude), `rayx::checked::tr!` |
| TS | `addI18n(configure?)`, `addMessageFormatter()`, and the classes `I18nService` and `I18nOptions` |
| Requires | `add_i18n`: `dyn AssetService` (`add_assets(..)`) and `dyn PlatformInfoService` (`add_platform()`); `add_message_formatter`: `dyn I18nService` (`add_i18n(..)`) |

```rust
use rayx::prelude::*; // `I18nAppBuilderExt`, `tr!`, `Args`, with the `i18n` feature

builder
    .add_platform()
    .add_assets(|_| {})
    .add_i18n(|options| {
        options.default_language("en").fallback_language("de");
    })
```

```tsx
new RayXAppBuilder()
  .addPlatform()
  .addAssets()
  .addI18n((options) => options.defaultLanguage("en").fallbackLanguage("de"));
```

`add_i18n` registers RayX's i18n service as the app's `dyn I18nService` and RayX's formatter over it as its
`dyn MessageFormatter` (it calls `add_message_formatter()`), replacing any earlier registration of either. Both are
startup services: the i18n service loads the asset catalog's translations when the app starts (after the asset
service, unless `auto_load_assets` is off) and then follows the platform service's languages and clock; the formatter
starts after it. It requires an [asset service](assets.md), which it loads its translations from, and a
[platform service](platform.md), and registers neither: building without one fails, naming it and what registers it.

`add_message_formatter()` registers RayX's formatter alone, over an i18n service of the app's own, in Rust or in TS
(see [Replace it](#replace-it)). In TS, `addI18n` and `addMessageFormatter` are there once the crate's set is
registered (`#[rayx::native_module]` with the feature on, or `rayx_services_i18n::register(registry)`).

## Configure

`I18nOptions` (`rayx_services_i18n::I18nOptions`) bind from `RayX:Services:I18N` (`I18N_CONFIG_PATH`), then the
closure changes them (in TS, the callback's methods of the same names, camelCase, after configuration's):

- `default_language` (`"en"`): the language messages fall back to last, and the one shown before the user's is known;
- `fallback_languages` (`fallback_language(..)` adds one): tried, in order, after the user's and before the default;
- `resources_path` (`"locales"`): the asset catalog's directory of translations;
- `default_namespace` (`"translation"`): the namespace whose ids are not prefixed;
- `auto_load_assets` (yes): loads every translation of the asset catalog at startup;
- `follow_platform` (yes): follows the platform's languages and clock until the app picks a language;
- `missing_message` (`MissingMessagePolicy::Id`, `"id"`; or `Empty`, `"empty"`): what a missing message shows;
- `bidi_isolation` (no): wraps placeholders whose direction is not the message's in Unicode isolates.

```json
{ "RayX": { "Services": { "I18N": { "defaultLanguage": "en", "fallbackLanguages": ["de"] } } } }
```

A language tag that does not read fails startup. The formatter takes the missing-message policy and bidi isolation
from these options; over an app's own service, `add_options::<I18nOptions>(..)` sets them.

### Translations

Translations are assets: `locales/<language>.json`, or `locales/<language>/<namespace>.json`, whose ids a namespace
other than the default one prefixes (`checkout.title`); nested objects make dotted ids. Every language loads at startup,
so changing the language is immediate.

Every package the [asset service](assets.md) reads can ship translations. A message several of them have comes from
the package listed first in the asset options, the app's own, so an app overrides the text of the libraries it uses;
the messages only a library has still come from it.

## The contract

`I18nService` (TS: `I18nServiceContract`) is NSH-free and implementable in Rust or TS.

Published state:

- `i18n()` (TS `i18n`): an `I18nState`: the language, the language the app chose (`chosen_language`, `None` while it
  follows the platform), the locale, the direction, the default and fallback languages, the languages the app has, the
  time zone, the messages as a `MessageBundle` per language (`{ language, messages: { id: source } }`) and a version.

Commands:

- `set_language(language)` (TS `setLanguage`): shows the app in that language from now on (`de`, `pt-BR`,
  `en-u-hc-h23`), whatever the platform reports later.
- `follow_platform()` (TS `followPlatform`): follows the platform's languages again.
- `load_messages()` (TS `loadMessages`): loads the app's messages (RayX's: every translation of the asset catalog);
  the ones that load are added, the error names the first that did not.
- `add_resource(language, namespace, json)` (TS `addResource`): adds a JSON resource's messages for `language`, in
  `namespace` (`None` for the default one), replacing messages with the same ids.
- `set_time_zone(zone)` (TS `setTimeZone`): shows instants in that IANA zone until the platform reports another.

Rust helpers (on `dyn I18nService`), reading the published state: `language()`, `chosen_language()`, `locale()`,
`direction()`, `available_languages()`, `time_zone()`, `version()`.

`MessageFormatter` (Rust only, not a contract): `t(id)`, `format(id, &args)`, `try_format(id, &args)`,
`format_to_parts(id, &args)` (text, values and markup, for rich text), `format_number(number, options)`,
`format_date_time(&value, options)`, `plural_category(number)`, `local_time(instant)`,
`local_time_from_millis(millis)`, `contains(id)` and `locale()`. `dyn MessageFormatter` is a `dxn_i18n::Translate`.

## Use

```rust
let i18n = services.required_service::<dyn I18nService>()?;
let formatter = services.required_service::<dyn MessageFormatter>()?;
let title = formatter.t("title");
let cart = formatter.format("cart", &Args::new().with("n", 3)); // "3 items"
i18n.set_language("de".into()).await?;
```

- The language follows the platform service's preferred languages and clock (the best of the app's languages for the
  user's list, with the user's region and `-u-hc-` hour cycle) until the app picks one with `set_language`;
  `chosen_language()` is that pick, and `follow_platform()` lets go of it.
- Messages are looked up through the language's parents, the fallback languages and the default one.
- `i18n().subscribe(..)` hears every change of language, time zone or messages.
- RayX's implementation answers `set_language`, `follow_platform`, `add_resource` and `set_time_zone` when called:
  `now_or_never()` gives the result at once (`load_messages` waits for the asset service). Its state is changed and
  published from any thread: each change is published under the next version, and the state published last is always
  the service's latest (a change made while another thread publishes is published right after, by that thread).
- The formatter is a `dxn_i18n::Translate`, as a `Translator` is, so dXn.I18n's `t!` (`rayx::i18n::t!`) and `args!`
  (re-exported from `rayx_services_i18n`) format with it, a reference or an `Arc` to it: `t!(formatter, "cart", n = 3)`,
  `formatter.format("cart", &args!(n = 3))`.

### Time zones

Instants are shown in the user's time zone: `time_zone()` is the platform's (an IANA name such as `Europe/Zagreb`),
else UTC, until the app sets one with `set_time_zone`. The formatter's `local_time(instant)` takes an RFC 3339 instant
with its offset (`2026-11-02T09:30:00Z`) and `local_time_from_millis(millis)` milliseconds after the Unix epoch; each
gives the wall time there, to format with `format_date_time` or pass as a message's date. The zones come from
dXn.Intl's `tz` feature and the IANA database it bundles.

## On NSH

In a Rust component, `tr!` (from `rayx_services_i18n`, and in `rayx`'s prelude) is the message in the app's language,
formatted by the surface's `dyn MessageFormatter`:

```rust
use rayx::prelude::*;

let name = "Ana";
text(move || tr!("cart.greeting", name, count = 3))
```

- The arguments are dXn.I18n's `args!`: they keep their types, so a number stays a number for `.match` and `:number`.
  A name is an identifier (a raw one without its `r#`) or a string literal for one Rust cannot spell
  (`"user-id" = 7`); a lone identifier passes the variable of that name, as `format!` does.
- Reading it subscribes, as reading a signal does: the text follows the app's start and every change of the language,
  time zone or messages, from any thread (from the formatter's startup on). Until the app is ready, without a message
  formatter, or outside an engine, it is the id.
- It is `tr!`, not `t!`: NSH's prelude has a `t!` for its own rust-i18n translations, and a glob import of both
  preludes keeps both.

`rayx_services_i18n::checked::tr!` (`rayx::checked::tr!`) is `tr!` with the call checked when the app builds, through
dXn.I18n's `dxn_i18n_macros`: a message id that is not in the app's messages (with the nearest one as a suggestion), an
argument no translation of the message reads, or one a translation needs and the call does not pass, fails the build
instead of showing the id or a fallback. Import it after the prelude, whose glob it then overrides:

```rust
use rayx::prelude::*;
use rayx::checked::tr;

text(move || tr!("cart.greeting", name, count = 3)) // error if `cart.greeting` is missing or takes other arguments
```

- It reads the crate's messages as the service's defaults have them: `assets/locales/<language>.json` or
  `assets/locales/<language>/<namespace>.json` beside `Cargo.toml`, every id in `en`, the `translation` namespace's ids
  unprefixed. An app whose options say otherwise says the same in its `Cargo.toml`:

  ```toml
  [package.metadata.dxn_i18n]
  messages = "assets/i18n"   # resources_path, under assets/
  default-locale = "de"      # default_language
  default-namespace = "app"  # default_namespace
  ```

- Its id is a string literal; `tr!` takes one made at run time. A change to a message file rebuilds the crate.

A language the app picks is NSH's too: from its startup on, RayX's formatter hands the i18n service's chosen language to
NSH's `set_locale`, so NSH's `locale()`, JS's `Intl` and NSH's own translations show it, and `follow_platform()` hands
NSH back to the device's languages. While the app follows the platform, NSH's locale is left alone, so a change of the
device's languages reaches both. This holds for any `I18nService` implementation the formatter follows.

NSH also reads rust-i18n translations from a `locales/` directory beside the app's `nsh.json` or `Cargo.toml`, at
build time. RayX's translations are assets in a package's `assets/locales/`, which NSH does not read; keep an app's
MessageFormat 2 files there, not in a top-level `locales/`.

## TSX

`I18nService`, resolved from the provider `start()` gives, wraps whichever `dyn I18nService` is registered and formats
synchronously through the app's `dyn MessageFormatter`:

- `t(id, args?)`, `has(id)`, `formatDate(instant, options?)`, `formatNumber(value, options?)`, `locale()`,
  `languages()`, `direction()` (`"ltr"` or `"rtl"`) and `timeZone()`, at once;
- `setLanguage(language)`, `followPlatform()`, `setTimeZone(zone)`, `loadMessages()` and
  `addResource(language, namespace, json)`: promises;
- `onChange(listener)`: hears the locale's tag after every change of the locale, the time zone or the messages; it
  returns a function that stops it.

```tsx
const i18n = services.getRequiredService(I18nService);
i18n.t("cart", { n: 3 });
i18n.t("sent", { at: date.toISOString() }); // a date in the user's time zone
i18n.formatDate(date.toISOString(), { length: "long", time: "minute" });
i18n.formatNumber(0.25, { style: "percent" });
await i18n.setLanguage("de");
const stop = i18n.onChange((locale) => refresh());
```

- `t` takes text, numbers, booleans and instants (`date.toISOString()`, a timestamp with its offset). A `Date` or any
  other object throws, because JavaScript hands it over as an empty object.
- `formatDate(instant, { length, date, time, hourCycle })`: `length` is `"short"`, `"medium"` (the default) or
  `"long"`; `date: false` leaves the date out; `time` (`"hour"`, `"minute"` or `"second"`) adds the time of day;
  `hourCycle` (`"h11"`, `"h12"`, `"h23"`, `"h24"`) overrides the locale's clock.
- `formatNumber(value, { style, currency, minimumIntegerDigits, minimumFractionDigits, maximumFractionDigits,
  useGrouping })`: `style` is `"decimal"` (the default), `"percent"` or `"currency"` with an ISO 4217 `currency`.
- The commands resolve once the service took them (a TS implementation's included, however long it takes) and reject
  with its error (an invalid language tag or time zone, a resource that did not load, what a TS implementation threw).
  `addResource`'s `namespace` is `null` for the default one, its `json` the resource's text.

## Replace it

Register the app's own `dyn I18nService` instead of calling `add_i18n`, and `add_message_formatter()` for RayX's
formatter over it (`tr!`, the TS class's formatting and NSH's locale then follow it):

```rust
builder
    .add_singleton_as::<dyn I18nService>(Arc::new(MyI18n::new()) as Arc<dyn I18nService>)
    .add_message_formatter()
```

One that must load at the start registers itself with `add_startup_singleton_for` in place of `add_singleton_as`,
as `add_i18n(..)` does: the trait and a startup service registered as it, which the formatter waits for
(`builder.add_startup_singleton_for::<dyn I18nService, _>(Arc::new(MyI18n::new()))`, `MyI18n` implementing
`AsyncInitializable` and `StartupInitializable`; [Startup](../startup.md#implementing-a-trait)). Registered
after `add_i18n(..)`, the app's own replaces it completely: RayX's never starts. An
app may also register its own `dyn MessageFormatter` instead of `add_message_formatter()`.

In TS, a class implementing `I18nServiceContract`, registered under the class `I18nService`
([contracts](../tsx.md#contracts)). It publishes an `I18nState` through a `ContractState`, with its messages as
`{ language, messages: { id: source } }` bundles (a field left out is its default, and `version` may be left out: the
formatter follows every publish):

```tsx
class MyI18n {
  i18n = new ContractState({ language: "en", locale: "en", default_language: "en", time_zone: "UTC" });
  isInitialized() { return (this.i18n.value.messages ?? []).length > 0; }
  async initialize() { await this.loadMessages(); }
  async loadMessages() {
    const messages = await fetchMessages();
    this.i18n.publish({ ...this.i18n.value, available_languages: ["en", "hr"], messages });
  }
  async setLanguage(language) {
    this.i18n.publish({ ...this.i18n.value, language, locale: language, chosen_language: language });
  }
  async followPlatform() {}
  async addResource(language, namespace, json) {}
  async setTimeZone(timeZone) { this.i18n.publish({ ...this.i18n.value, time_zone: timeZone }); }
}

new RayXAppBuilder()
  .addStartupSingletonAs(I18nService, () => new MyI18n())
  .addMessageFormatter();
```

`rayx_app::testing::FakeI18n` is a fake of the contract (it applies the commands to its state as RayX's does) and
`FakeMessageFormatter` one of the formatter, for testing what consumes them.
