# I18n

Translations with MessageFormat 2 messages, and numbers, dates and plurals formatted for the user's locale. I18n is two
abstractions in `rayx_app::services::i18n`:

- `I18nService`, a contract: the app's languages and messages, published as `I18nState` (the language, the language the
  app chose, the locale, the direction, the default and fallback languages, the languages the app has, the time zone,
  the messages as a bundle per language, and a version), with async commands `set_language`, `follow_platform`,
  `load_messages`, `add_resource` and `set_time_zone`. Its data cross to TS, so a TS implementation can load messages
  from anywhere.
- `MessageFormatter`, Rust only and synchronous: `t`, `format`, `try_format`, `format_to_parts`, `format_number`,
  `format_date_time`, `plural_category`, `local_time` (and `contains`, `locale`, `local_time_from_millis`), over
  whichever `dyn I18nService` is registered. It compiles the service's messages per language with
  [dXn.I18n](https://github.com/dXnSix/dXn.I18n) and formats with [dXn.Intl](https://github.com/dXnSix/dXn.Intl)
  (ICU4X), the same on every platform, and compiles them again when the service publishes a new version.

RayX's implementations of both are `rayx_services_i18n`'s.

## Register

```rust
use rayx_services_i18n::I18nAppBuilderExt as _;

builder.add_i18n(|options| {
    options.default_language("en").fallback_language("de");
})
```

`add_i18n` registers RayX's i18n service as the app's `dyn I18nService` and RayX's formatter over it as its
`dyn MessageFormatter` (`builder.addI18n(..)` in TS, once the crate's set, `rayx_services_i18n::register(registry)`, is
registered). It requires an [asset service](assets.md) (`add_assets(..)`, or the app's own `dyn AssetService`), which
it loads its translations from, and a [platform service](platform.md) (`add_platform()`, or the app's own
`dyn PlatformInfoService`), whose languages and clock it follows, and registers neither: building without one fails
naming it. RayX's i18n service initializes after the asset service, and the formatter after the i18n service.

`add_message_formatter()` (`builder.addMessageFormatter()` in TS) registers RayX's formatter alone, over an i18n service
of the app's own, in Rust or in TS (`addSingletonAs(I18nService, () => new MyI18n())`).

## Configure

`I18nOptions` bind from `RayX:Services:I18N`, then the closure changes them: the default language, the fallback
languages, the resources path (`locales`), the default namespace, automatic loading of the asset catalog's
translations, following the platform's languages, the missing-message policy and bidi isolation. The formatter takes
the last two from them (over an app's own service, `add_options::<I18nOptions>(..)` sets them).

```json
{ "RayX": { "Services": { "I18N": { "defaultLanguage": "en", "fallbackLanguages": ["de"] } } } }
```

## Translations

Translations are assets: `locales/<language>.json`, or `locales/<language>/<namespace>.json`, whose ids a namespace
other than the default one prefixes (`checkout.title`). Every language loads at startup, so changing the language is
immediate.

Every package the [asset service](assets.md) reads can ship translations. A message several of them have comes from
the package listed first in the asset options, the app's own, so an app overrides the text of the libraries it uses;
the messages only a library has still come from it.

## Use

```rust
let i18n = services.required_service::<dyn I18nService>()?;
let formatter = services.required_service::<dyn MessageFormatter>()?;
let title = formatter.t("title");
let cart = formatter.format("cart", &Args::new().with("n", 3)); // "3 items"
i18n.set_language("de".into()).await?;
```

- The language follows the platform service's preferred languages and clock (the best of the app's languages for the
  user's list, with the user's region and `-u-hc-` hour cycle) until the app picks one with `set_language`;
  `chosen_language()` is that pick, and `follow_platform()` lets go of it.
- Messages are looked up through the language's parents, the fallback languages and the default one.
- `language()`, `locale()`, `available_languages()`, `direction()`, `time_zone()` and `version()` read the published
  state; `i18n().subscribe(..)` hears every change of language, time zone or messages.
- RayX's implementation answers its commands when called: `now_or_never()` gives the result at once. Its state is
  changed and published from any thread: each change is published under the next version, and the state published
  last is always the service's latest (a change made while another thread publishes is published right after, by that
  thread).
- The formatter is a `dxn_i18n::Translate`, as a `Translator` is, so dXn.I18n's `t!` and `args!` (re-exported from
  `rayx_services_i18n`) format with it, a reference or an `Arc` to it: `t!(formatter, "cart", n = 3)`,
  `formatter.format("cart", &args!(n = 3))`.

## On NSH

In a Rust component, `tr!` (from `rayx_services_i18n`, and in `rayx`'s prelude) is the message in the app's language,
formatted by the surface's `dyn MessageFormatter`:

```rust
use rayx::prelude::*;

let name = "Ana";
text(move || tr!("cart.greeting", name, count = 3))
```

- The arguments are dXn.I18n's `args!`: they keep their types, so a number stays a number for `.match` and `:number`.
  A name is an identifier (a raw one without its `r#`) or a string literal for one Rust cannot spell
  (`"user-id" = 7`); a lone identifier passes the variable of that name, as `format!` does.
- Reading it subscribes, as reading a signal does: the text follows the app's start and every change of the language,
  time zone or messages, from any thread (from the formatter's startup on). Until the app is ready, without a message
  formatter, or outside an engine, it is the id.
- It is `tr!`, not `t!`: NSH's prelude has a `t!` for its own rust-i18n translations, and a glob import of both
  preludes keeps both.

`rayx_services_i18n::checked::tr!` (`rayx::checked::tr!`) is `tr!` with the call checked when the app builds, through
dXn.I18n's `dxn_i18n_macros`: a message id that is not in the app's messages (with the nearest one as a suggestion), an
argument no translation of the message reads, or one a translation needs and the call does not pass, fails the build
instead of showing the id or a fallback. Import it after the prelude, whose glob it then overrides:

```rust
use rayx::prelude::*;
use rayx::checked::tr;

text(move || tr!("cart.greeting", name, count = 3)) // error if `cart.greeting` is missing or takes other arguments
```

- It reads the crate's messages as the service's defaults have them: `assets/locales/<language>.json` or
  `assets/locales/<language>/<namespace>.json` beside `Cargo.toml`, every id in `en`, the `translation` namespace's ids
  unprefixed. An app whose options say otherwise says the same in its `Cargo.toml`:

  ```toml
  [package.metadata.dxn_i18n]
  messages = "assets/i18n"   # resources_path, under assets/
  default-locale = "de"      # default_language
  default-namespace = "app"  # default_namespace
  ```

- Its id is a string literal; `tr!` takes one made at run time. A change to a message file rebuilds the crate.

A language the app picks is NSH's too: from its startup on, RayX's formatter hands the i18n service's chosen language to
NSH's `set_locale`, so NSH's `locale()`, JS's `Intl` and NSH's own translations show it, and `follow_platform()` hands
NSH back to the device's languages. While the app follows the platform, NSH's locale is left alone, so a change of the
device's languages reaches both. This holds for any `I18nService` implementation the formatter follows.

NSH also reads rust-i18n translations from a `locales/` directory beside the app's `nsh.json` or `Cargo.toml`, at
build time. RayX's translations are assets in a package's `assets/locales/`, which NSH does not read; keep an app's
MessageFormat 2 files there, not in a top-level `locales/`.

## Time zones

Instants are shown in the user's time zone: `time_zone()` is the platform's (an IANA name such as `Europe/Zagreb`),
else UTC, until the app sets one with `set_time_zone`. The formatter's `local_time(instant)` takes an RFC 3339 instant
with its offset (`2026-11-02T09:30:00Z`) and `local_time_from_millis(millis)` milliseconds after the Unix epoch; each
gives the wall time there, to format with `format_date_time` or pass as a message's date. The zones come from
dXn.Intl's `tz` feature and the IANA database it bundles.

## TSX

`I18nService`, resolved from the provider `start()` gives, wraps whichever `dyn I18nService` is registered and formats
through the app's `dyn MessageFormatter`:

```tsx
const i18n = services.getRequiredService(I18nService);
i18n.t("cart", { n: 3 });
i18n.t("sent", { at: date.toISOString() }); // a date in the user's time zone
i18n.formatDate(date.toISOString(), { length: "long", time: "minute" });
i18n.formatNumber(0.25, { style: "percent" });
i18n.setLanguage("de");
i18n.onChange((locale) => refresh());
```

- `t` takes text, numbers, booleans and instants (`date.toISOString()`, a timestamp with its offset). A `Date` or any
  other object throws, because JavaScript hands it over as an empty object.
- `formatDate(instant, { length, date, time, hourCycle })`: `length` is `"short"`, `"medium"` (the default) or
  `"long"`; `date: false` leaves the date out; `time` (`"hour"`, `"minute"` or `"second"`) adds the time of day;
  `hourCycle` (`"h11"`, `"h12"`, `"h23"`, `"h24"`) overrides the locale's clock.
- `formatNumber(value, { style, currency, minimumIntegerDigits, minimumFractionDigits, maximumFractionDigits,
  useGrouping })`: `style` is `"decimal"` (the default), `"percent"` or `"currency"` with an ISO 4217 `currency`.
- `setLanguage(language)`, `followPlatform()` and `setTimeZone(zone)` call the service's commands (a TS
  implementation's on the engine's next turn).
- `timeZone()` is the zone instants are shown in; `onChange` hears changes of the locale, the time zone and the
  messages, until the function it returns is called.

A TS implementation of the contract (`I18nServiceContract`) publishes an `I18nState` through a `ContractState`, with
its messages as `{ language, messages: { id: source } }` bundles; registered under the class with
`addSingletonAs(I18nService, () => new MyI18n())` and `addMessageFormatter()`, the class formats its messages.
